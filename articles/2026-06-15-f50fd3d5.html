花 8 萬請工程師，Codex 到底能取代多少？

花 8 萬請工程師，Codex 到底能取代多少？

上週有個做電商後台的老闆傳訊息給我，問題很直接：「我現在花 8 萬請工程師，聽說 Codex 出來之後可以取代？你給我一個說法。」

我當下沒有馬上回答。不是不知道，是因為這個問題問錯了——或者說，問這個問題的方式，決定你拿到的答案大概率沒什麼用。

這個道理其實跟易經的問法邏輯一樣。你怎麼問，決定你看到什麼。等一下再說。

先說 Codex 能做什麼。

Codex 真正能做的事

Codex 是 OpenAI 推出的 coding agent，可以在 GitHub 環境裡，接受自然語言指令去寫程式碼、跑測試、修 bug、開 pull request。

它可以做的事情包含：把你用白話描述的功能需求轉成可執行程式碼、在現有 repo 裡找 bug 然後嘗試修復、寫單元測試、做程式碼格式整理或重構、翻找文件回答「這段 code 在幹嘛」。

這些工作，一個初級工程師每天可能要花 30–40% 的時間在做。

如果你請的工程師主要工作是「把需求單轉成功能」「維護既有系統」「修幾個不大不小的 bug」，那 Codex 確實可以承接很大一部分。

但問題不在「它會不會」，問題在「它能不能獨立完成」。

所謂獨立完成，是從你描述需求，到功能跑起來上線，中間完全不需要人介入。目前做不到。

它會卡在幾個地方：環境設定太複雜的 repo，它會搞不定。涉及多個系統串接（ERP、金流、第三方 API）的任務，它可以寫程式碼，但不一定知道你的系統架構是什麼、例外狀況怎麼處理。測試通過但上線後跑起來跟預期不同，它沒辦法自己意識到。還有產品方向的判斷——這個功能現在要不要做、這個邏輯設計合不合理——這完全不是 Codex 的能力範圍。

8 萬元，你在請什麼樣的工程師

中小企業在請工程師這件事上，最常犯的錯誤是把「技術執行」跟「技術判斷」混在一起。

8 萬元的工程師，你請他來做什麼？

如果他的主要工作是「你說什麼他做什麼」，那 Codex 加上一個懂得寫清楚需求的人，大概可以把這部分工作量切掉 60–70%。我不是預估，是實際陪幾個客戶跑過之後的觀察。

有一家做連鎖加盟管理系統的公司，原本月費 6.5 萬請外包工程師維護後台，後來改成 Codex 搭配一位非工程師背景的產品管理人員，每個月費用降到不到 2 萬，功能交付速度沒有變慢，bug 因為有寫測試反而少了。

但那位工程師做的另外一件事——幫他們評估新功能架構、在系統轉型時比較幾個方案的風險——這沒有被取代，反而他們後來找一個更資深的人以顧問方式合作，費用比以前整份薪水還高。

這是我觀察到的現實：Codex、Claude Code 這類 coding agent，正在把初級工程師的執行工作自動化。它不是在消滅工程師這個職業，而是在重新分配——執行性質的工作交給 AI，判斷性質的工作反而更值錢。

所以企業 AI 導入不是「取代人」，而是「重新定義人該做什麼」。

易經的問法：你在問什麼問題

我說要回到問法這件事。

易經裡有個概念叫「貞」，有種解釋是「問卜前要先把問題想清楚」。你問的是泛問題還是精問題，得到的訊息完全不同。

一個老闆問「Codex 可以取代工程師嗎」，跟另一個老闆問「我目前的工程師每週工作量裡，哪些部分是可以被 AI 工具取代的」，這兩個問題的答案差非常遠。

前者讓你陷入沒有結論的辯論。後者讓你開始做 audit——盤點工程師的時間分配，找出哪些是重複性任務、哪些是判斷性任務，然後決定哪段最適合先嘗試用 Codex 替換。

中小企業數位轉型最常死在這裡。不是技術不夠好，是問題沒問清楚就直接買工具、請顧問、換系統，做一半發現方向不對，再從頭來過。

我遇過一個做精密零件加工的公司，老闆很積極，聽說 AI 可以幫做程式碼就去找 Codex，結果他工廠的核心問題是生產排程太亂，Codex 幫不上——它能寫程式碼，但不能替你決定排程邏輯應該長什麼樣子。那是流程設計的問題，不是寫程式的問題。浪費了三個月。

如果你想試，我建議這樣開始

不要先問「能不能取代」，改問「我現在哪一塊技術工作最讓我頭痛」。

這個答案說出來，通常就很清楚 Codex 能不能幫上忙了。如果你說「工程師每次修 bug 都要等好幾天」，那可以試。如果你說「我不確定這個系統架構下去能不能支撐未來的成長」，那 Codex 幫不了你，你需要的是技術架構師的判斷。

真的要評估，就拿一個真實任務去測試，不要看 demo。Codex 的 demo 都很漂亮。你要做的是把自己的 repo 丟進去，給它一個真實的任務——比如「在這個後台新增一個匯出 Excel 的功能，格式是這樣」——然後看結果你能不能直接用。

還有一件事很多人沒想到：成本不是只算工具費用，要算「你要花多少時間學會用它」。Codex 不難用，但要用得好，你要懂得寫清楚的需求，能看懂它給你的程式碼大概在做什麼，能判斷「這個結果對不對」。如果你或你的團隊完全沒有技術背景，這段學習曲線要有心理準備，不能跳過。

---

我沒辦法給你一個「Codex 可以讓你省 X 萬」的公式，因為差異太大，取決於你現在在請什麼樣的人做什麼樣的事。

但我可以說清楚一件事：問「能不能取代」本身沒有太大意義。你要問的是「我有沒有把對的問題交給對的工具」。

這一點，易經也好，AI 也好，道理是一樣的。

常見問題

Codex 跟 Claude Code 有什麼差別，中小企業選哪個？
Codex 是 OpenAI 的，偏向在 GitHub 環境裡的 agent 操作，需要你有 repo 才跑得起來。Claude Code 是 Anthropic 的，更偏向你在終端機或本地環境與它互動，適合邊開發邊問問題。兩個都在快速更新，能力差距每個月在縮小。如果你本來就在用 GitHub 管理程式碼，Codex 上手路徑比較直；如果你沒有特定偏好，Claude Code 的對話式開發流程很多工程師覺得比較自然。
我完全沒有技術背景，可以用 Codex 嗎？
可以用，但你需要一段適應期。Codex 接受自然語言，不用懂程式碼就能下指令，但你要能判斷它給出的結果「有沒有真的完成你要的功能」，這需要一點基本認識。比較實際的做法是找一個懂技術的人幫你驗收——你負責描述需求，他負責確認成果。這樣的搭配，才能發揮效率，也不會因為看不懂輸出而踩雷。
想試 Codex，第一步應該怎麼做？
不要上來就把主力系統丟進去。先挑一個「就算搞壞也沒關係」的小功能或內部工具，在那個範圍裡測試它的能力。跑完之後，你對它能做什麼、不能做什麼，會有一個實際感受，比看任何教學文章都更有用。第一個任務最好控制在一到兩天能跑完、成果能驗證的範圍內，不要一開始就給太大的任務。
