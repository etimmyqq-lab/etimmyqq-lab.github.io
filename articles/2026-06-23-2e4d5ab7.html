介紹型 vs 操作型

去年四月，新竹一家做被動元件的廠商找我去看他們的「每週 AI 分享會」。

他們已經辦了三個月，每週三下午兩點，IT 主管準備二十分鐘投影片，介紹一個 AI 工具，開放問答，然後散會。

我去那天，會議室坐了十四個人。九個低頭看手機，兩個在接 Line，一個在吃東西，最後一個是 IT 主管，在台前很認真地講著。

二十分鐘過去，散會。我問那個主管：「你覺得效果怎樣？」

他說：「不知道，沒有人給我回饋。」

這種情況，我在不同產業的公司見過好幾次。食品廠、電子代工廠、傳統貿易商，都有類似的狀況：辦了很久的分享會，主講人認真準備，但成效模糊，三四個月之後有時候就悄悄停辦了。

不是人的問題，是設計問題。

介紹型 vs 操作型

大多數企業 AI 分享會的邏輯是這樣的：每週找一個人來準備，其他人來聽，聽完之後回去自己試試看。這個邏輯在學校教室可能成立，但在企業環境裡，幾乎從來不成立。

原因很簡單。「回去之後試試看」這件事根本不會發生。每個人散會之後都有自己的事在等著，有報表要交，有客戶要回，有下一個會議要進去。「試試看那個上週分享的工具」根本排不進任何人的工作清單裡。

我把這兩種設計分別稱為「介紹型」和「操作型」。

介紹型的目標：你知道這個工具存在。

操作型的目標：你在這三十分鐘內做完一件事，哪怕只是打開帳號、輸入第一行文字、生成一份草稿。

三個月後，兩種設計的差距非常明顯。介紹型的，大家多認識了幾個工具的名字，但工作流程幾乎沒有變。操作型的，至少有兩三個人開始在日常工作裡真的用上了什麼。

我實際在用的分享會結構

這個結構是帶了很多場之後改出來的，不是從哪本書上照搬的，是踩過幾個彎路以後留下的版本。

第一段：前五分鐘，設定一個今天要解決的具體問題。

不是「今天我們來了解 Claude Code」，而是「今天我們要用 Claude Code 幫業務部做一份詢價回覆的模板，業務下週一要用的那種」。

有了具體目標，人才知道自己今天學到了什麼，也才能評估「這對我有沒有用」。沒有目標的話，分享結束只能說「喔蠻有趣的」然後散會，說不上是學到還是沒學到。

這個問題最好在分享會前一兩天就問好。去問一線員工或他們的主管：「你們最近工作上有什麼事情最花時間？」這個動作本身就是在準備土壤，讓接下來的分享落地。什麼問題比較適合？通常是「每次都要從頭寫」「格式不固定」「要對照好幾個資料來源才能回答」這類重複性高、但需要判斷的工作，Claude Code 在這種場景下幫得上。

第二段：中間二十分鐘，帶著做，不是你示範我看著。

這是我見過最多分享會搞錯的地方。主講人在台前操作，其他人在旁邊看，看完了，「好，這樣就學會了。」

效率比你想的低很多。看別人做一遍和自己做一遍，感受完全不同。卡住的那一刻，才是真正學習發生的地方。你看到流暢的示範，回到座位之後腦子裡是一片空白，因為你沒有被那個「卡住感」激活過。

所以我的分享會，主講人操作五分鐘，剩下十五分鐘是每個人自己動手試，遇到問題就說出來，大家一起解決。有人帳號打不開，有人 prompt 寫錯了，有人不知道結果貼去哪裡，這些都正常，當場解決的價值遠高於看一個流暢的示範。

第三段：最後五分鐘，請一個學員說他今天遇到了什麼、怎麼解的。

不是主講人來總結，是學員說。說得不完整也沒關係，說錯了也可以，旁邊的人可以補充。這個動作的作用是讓知識從「別人說過的經驗」變成「我說出口的東西」。腦子裡想過和嘴巴說出來是兩件事。開口說過的人，下次有人問他「你們公司有沒有在用 AI」，他會說「有，我上週用過，用在這件事上」，而不是「好像有人分享過什麼工具」。

易經說的「時」和分享會的節奏

這一段有些人可能覺得跳，但我還是說一下。

易經裡有個概念叫「時」，不是時鐘的時間，是「現在做這件事，時機是不是對的」那個判斷。

我在陪廠商做企業 AI 導入的諮詢時，最常被問到的問題之一是：「我什麼時候適合在公司開始推 AI？」

這個問題和「每週 AI 分享會怎麼設計才有效」是同一個問題的不同層次。格式設計對，固然重要，但如果公司正在年終衝刺、業務最後拚量的那兩三週，那場分享會就算設計得再好，吸收率也不會高。人的注意力放在別的地方，沒有餘裕真的進去。

易經的「觀察時機」不是算命，是提醒你注意：這個動作現在做，土壤準備好了嗎？

對 AI 分享會來說，我觀察到幾個「土壤準備好了」的訊號：

有一個人最近正在解決一個具體問題，而那個問題 AI 可能幫得上。公司剛剛發生了一件大家都知道的麻煩，有人在抱怨某個流程太耗時。老闆最近在聊天裡問過「這件事 AI 能不能做」。

這幾個訊號出現的時候去辦分享會，效果比沒有訊號的時候要好很多。那個問題的土壤已經翻開了，種進去的東西才會長。沒有這些訊號的時候，硬辦一場，種下去的東西可能直接就死在那裡。不是種子的問題，是土的問題。

IT 主管隔週調整了設計。他在分享前先去問業務主管：「你們報價流程哪裡最花時間？」

業務說：「寫詢價回覆。每次格式都不太一樣，要從頭想，一封大概要花二十分鐘。」

那週的分享會，他拿這個問題來，帶大家用 Claude Code 試著做一份回覆模板。三十分鐘。結束之後，兩個業務說想繼續試。一個說下週要把這個模板拿去跟客戶用。

沒有人低頭看手機。

格式和之前完全一樣，三十分鐘，同一個會議室，同一批人。不一樣的是，那個問題是現在就有人在頭痛的事。土壤翻開了，種進去才會長。

就這樣。

常見問題

每週一次 AI 分享會，頻率是不是太高？
問題不在頻率，在每次有沒有讓人完成一個動作。每週三十分鐘、每次做一件具體的事，三個月後整個團隊的使用習慣會很不一樣。但如果每次都只是介紹工具、看示範，就算每週辦、年年辦，半年後也不會有太大差別。我陪企業做 AI 導入時，通常建議從雙週一次開始，品質穩了之後再調整成每週。
公司沒有 IT 背景的人，適合辦 AI 分享會嗎？
適合，而且建議讓非 IT 背景的人來主講。業務或行政分享「我用 Claude Code 怎麼處理我自己的問題」，說服力反而更強，因為聽的人會覺得「這件事我也能做」，而不是「這是工程師的事，跟我無關」。
主管要不要一起參加分享會？
要，而且要坐前面跟著試，不是坐後面旁觀。我見過太多公司，員工學會了用 Claude Code，但主管沒有在用，結果員工也不敢在正式工作上用。如果主管在分享會上試了一下、說了一句「這個可以幫我做週報」，整個氣氛完全不同。
