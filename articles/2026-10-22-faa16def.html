補全跟交辦，是兩個不同的動作

十月九號晚上八點多，一位在包裝材料公司管 ERP 報表的工程師傳訊息問我：「我 VS Code 的補全套件都裝好了，還需要特別去學 Codex 嗎？」我沒直接回答，先問他一件事：你每個月月初那份跨廠區耗料比對表，現在要做幾天？

他說兩天半。

他裝補全套件已經三個月。他自己估，寫程式的手速大概快了三成，寫 API、寫迴圈、補 try except，這些確實省時間。但那份兩天半的報表，一分鐘都沒有變快。

我當下就知道他問錯問題了。

補全跟交辦，是兩個不同的動作

補全型的工具，前提是你心裡已經有譜。你知道下一行大概長什麼樣，只是手指還沒打完，它幫你把打字的時間省掉。你寫 `for row in`，它接著給你一段迴圈，你瞄一眼，對，就收下。這個動作的本質是加速。

在終端機裡跑的那一類（Codex、Claude Code 這種），動作完全不同。你給它一段需求，它自己決定要開哪幾個檔案、讀什麼欄位、寫什麼、然後跑起來、看到錯誤、回去改、再跑。你不是在補一行，你是在交辦一件事。這個動作的本質是委派。

兩個都開著一點都不衝突。我自己電腦上兩邊都在，看我那個小時在做哪種事。

所以不要問該裝哪一個。要問的是：你一天裡面，有多少時間是「知道要寫什麼只是手慢」，有多少時間是「只有一句需求，連檔案都還沒建」。

那位工程師的卡點，顯然不在手速。

他那份兩天半的報表，到底難在哪

我請他把來源資料列給我看。六個 Excel：四個廠區的領料明細、一份 BOM、一份換算規則——這份規則是前任留下來的，手寫在一個 Word 檔裡，十一條，其中三條互相有例外。另外兩個是從 ERP 匯出的 CSV，欄位名稱還跟 Excel 對不上。

這件事裡面沒有任何一行是「他知道要寫什麼只是手慢」。他根本不知道第一行該寫什麼。他過去兩年的做法是：開六個視窗，用眼睛跟 Ctrl+F 對，對完手動填進總表。

補全幫不上他。不是補全不好，是這個位置上沒有東西可以補，它不知道他要往哪裡去。

那天晚上我們做的第一件事，是叫它先不要動手。

常見問題

那我兩個都裝，會不會互相打架？
不會。它們管的範圍不一樣，一個在編輯器裡接你的下一行，一個在終端機裡自己開檔案跑。我自己電腦上兩邊都開著，寫熟悉的 SQL 就靠補全，遇到「月初那包報表要重做」這種就丟到終端機。唯一要注意的是同一個檔案不要兩邊同時改，不然 git diff 會很難看。
我這種只會寫一點 Python 的 ERP 人員，學終端機那套會不會太硬？
硬的地方不是指令，是你要學會把需求講清楚。指令本身大概十分鐘就會了。真正卡住人的是——你能不能寫出「讀 A 廠跟 B 廠這兩個 CSV，用料號對，列出數量差超過 5% 的」這種句子。那位工程師第一次寫需求寫了三行，跑出來的東西完全不對，第二次補上欄位名稱才對。所以不是技術門檻，是描述能力。
那兩天半的報表，換成終端機工具真的會快嗎？
我老實講，不一定會變成十分鐘。他那份報表第一次跑通花了快兩小時，光是搞清楚舊檔案的欄位編碼就花了半小時。但第二個月再跑就是五分鐘的事，因為腳本留下來了。所以省時間不在第一次，在第二次以後。如果那份報表一年只做一次，說實話不太值得。
